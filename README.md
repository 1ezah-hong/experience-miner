# Experience Mapping

一个用于**经历还原与结构化梳理**的 Agent Skill。

它不会直接把经历包装成简历，也不会为了“看起来完整”而补全不存在的成果。它更关注：你当时到底处在什么位置、做了什么、做过哪些判断、结果属于谁的负责范围，以及哪些信息仍然未知。

GitHub：https://github.com/1ezah-hong/experience-miner

## 适合什么场景

当你想梳理以下经历时，可以使用本 Skill：

- 实习 / 工作经历
- 项目经历
- 课程经历
- 校园 / 社团经历
- 志愿经历
- 研究经历
- 其他需要回顾和还原的个人经历

它既支持纯文本叙述，也可以结合简历、截图、PDF、表格、周报、项目文档等已有材料进行梳理。

如果你的需求只是简历润色、措辞优化、内容改写或排版调整，而不涉及经历本身的回顾、补充与澄清，则不适合使用本 Skill。

## 它会做什么

Experience Mapping 会围绕以下问题逐步还原经历：

- 当时发生了什么？
- 为什么会有这件事？
- 你当时处在什么位置？
- 你实际做了什么？
- 哪些事情是你主动判断或推动的？
- 哪些结果属于你的直接负责范围？
- 哪些结果属于团队共同成果？
- 哪些后续情况你并不了解？
- 中间发生过哪些变化、困难或调整？
- 现在回头看，你对这段经历有什么新的理解？

核心原则：

- 事实优先，不补不存在的事实
- 区分“参与”“负责”“主导”“支持”
- 区分动作、判断、贡献和结果
- 不把团队成果自动归给个人
- 也不因为存在团队协作，就弱化用户直接负责范围内的个人成果
- 不强行补成完整闭环
- 允许“结果未知”“项目未完成”“只参与一个阶段”
- 信息足够时停止追问，不无限盘问

## 安装

### 方式一：仅在当前 Codex 项目中使用

把 Skill 放到项目目录：

```text
your-project/
└── .codex/
    └── skills/
        └── experience-mapping/
            └── SKILL.md
```

这种方式适合把它作为某个项目的专用 Skill。

### 方式二：作为用户级 Skill 使用

把 Skill 放到：

```text
~/.codex/skills/experience-mapping/SKILL.md
```

这样它可以在不同 Codex 项目中被发现和使用。

## 使用

可以显式调用：

```text
$experience-mapping

我想梳理一段实习经历。
我记得自己参加过一个创作者活动，主要做了通知和报名整理，
但现在说不清自己到底负责了什么。
```

也可以直接描述需求，让 Codex 根据 Skill 的 `name` 和 `description` 判断是否调用：

```text
我想系统梳理一下大二参加社团活动的经历，
现在很多细节已经记不清了。
```

如果有材料，也可以一起提供：

```text
$experience-mapping

这些截图和周报是我当时的工作材料。
请先基于材料和我的补充还原经历，不要直接改写成简历。
```

## 输出

最终输出是一份**经历梳理记录**，可能包括：

- 经历概览
- 时间与阶段
- 角色与关系
- 目标与任务
- 具体行动
- 关键判断与选择
- 协作过程
- 关键变化与困难
- 结果与影响
- 个人贡献与结果归属
- 认知与反思
- 待补充信息

这些栏目不是必须全部出现。没有足够事实支持的部分可以省略。

## 示例

用户：

> 我参加过一个创作者活动，就是发通知、整理报名。团队最后招募了 100 人，但我不知道自己算有什么贡献。

合适的第一轮不是直接总结“体现了运营能力”，而是先继续确认：

- 你负责通知全部创作者，还是其中一部分？
- 整理报名时，你具体处理过什么问题？
- 你整理好的信息最后交给谁、用于什么环节？

在事实没有确认前，不把“100 人”直接写成用户个人成果；如果后续能够确认这一结果确实发生在用户直接负责范围内，也不应因为项目存在团队协作而自动将其降级为“团队成果”。

## 当前版本

**V2**

V2 重点修复了结果归属中过度保守的问题：

- 防止把团队成果误归给个人
- 防止把用户直接负责范围内的成果错误弱化成团队成果
- 结果归属依据职责范围、实际行动和结果对象之间的对应关系判断

详细变化见 [CHANGELOG.md](./CHANGELOG.md)。
